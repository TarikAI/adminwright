# Community observations

Contributed, sanitised observations from real Adminwright builds. Entirely opt-in.

## What this is for

The promotion bar in [../references/skill-evolution.md](../references/skill-evolution.md)
asks whether a lesson was seen on two or more **distinct projects**. One person working
alone answers that slowly. Contributions let evidence accumulate faster, without anyone
handing over their code.

Community records **corroborate**. They never adopt guidance on their own, and `promote`
enforces it: a candidate made only of contributed records, however many or whatever their
category, is listed apart as "community only (not eligible)" until a sighting in your own
store joins it. They are labelled in `promote` output so a reviewer can weigh them
differently, each contributed record counts as one project whatever its `projects` list
says, and every change to the references still goes through the same review as any other
pull request.

## What a bundle contains

Generated by `promote --export`, and nothing else is accepted:

- the promotion candidate's category, scope, observation and proposed change, with emails,
  URLs, file paths, IP addresses, hostnames, domains, tokens and hashes replaced by markers
  (the full list is in [../PRIVACY.md](../PRIVACY.md)); the scope only when it names a file
  or area of the skill, otherwise `unassigned`
- project names replaced by one-way fingerprints salted per store, so no project is
  identifiable. Fingerprints are countable only within bundles from one store: the same
  project exported from two stores (two devices, or a store created again) appears as two
- stacks coarsened to family names (`postgres`, `next.js`) rather than versions or hosts
- **no** fingerprint of the observation text, **no** evidence paths, **no** manifest,
  **no** code

The exporter prints a warning that no pattern can catch a company or person's name written
as an ordinary word. Read your bundle before opening a pull request. Reviewers will too, but
you are the only one who can recognise your own customer's name.

## Contributing

```bash
python <skill-dir>/scripts/admin_console_manifest.py promote --export my-bundle.json
```

Read the file. Then open a pull request adding it as
`community/observations/<something-descriptive>.json`. Use the "Lesson from a real build"
issue template if you would rather discuss it first.

## Using contributions

```bash
python <skill-dir>/scripts/admin_console_manifest.py promote --include-community
```

Community records are merged into the bar calculation and marked in the output. They count
toward a candidate only beside at least one observation from your own store; a bundle that
your own store exported is recognised by its fingerprints and never corroborates itself. To
contribute from several devices, export from one store, or say in the pull request that two
bundles are yours so a reviewer does not count your projects twice.

## Withdrawing

Open a pull request deleting your file. No questions asked, no copy kept. Because
contributions are plain files in git history, a full erasure additionally requires a history
rewrite — say so in the pull request if that is what you need.

## What is never accepted here

Raw manifests, code, logs, screenshots, customer data, anything unsanitised, and anything
generated by hand rather than by `promote --export`. Pull requests containing them will be
closed rather than edited, because a partial scrub is worse than an obvious one.
