## Why this check comes first

Building an admin console from scratch is the default an agent reaches for and frequently the
wrong one. Three weeks rebuilding a worse version of Django admin is a real and common
outcome.

Run this check during discovery, before modeling screens. It is cheap: read the dependency
manifest, look for an existing admin, and ask whether the domain's complexity actually
exceeds what a framework handles.

The check has three outcomes: adopt, hand-build, or the hybrid in section 5. The hybrid is
correct more often than either extreme.

## Check what the stack already ships

| Stack | Ships | Ceiling |
|---|---|---|
| Django | `django.contrib.admin` | Model editing, not workflow. Add/change/delete/view permissions cannot express scope conditions or transition preconditions |
| Laravel | Filament, Nova | Strong resource CRUD and forms; scoped authorization and approval flows still need policies you write |
| Rails | ActiveAdmin, Administrate | Similar shape to Django admin, similar ceiling |
| Supabase | Studio | A database console for developers, not an operator console. No domain commands, no per-operator scope |
| Medusa, Payload, Directus, Strapi | A product admin | Excellent for the entities they model, thin for custom lifecycle commands and multi-tenant scope |
| Cloud providers | Their own consoles | Useful for infrastructure, never for your domain |

If one of these exists in the repository already, the question is not whether to use it but
where its ceiling is and what belongs on the other side of it.

## Accelerators and their ceilings

| Tool | Accelerates | Breaks down when | Authorization model |
|---|---|---|---|
| [Refine](https://refine.dev/docs/) | React CRUD with routing, auth, access control, audit-log and realtime hooks already modeled | Deeply custom workflow screens that fight the resource abstraction | Pluggable access-control provider; adequate, but the policy is still yours to write and enforce server-side |
| [react-admin](https://marmelab.com/react-admin/documentation.html) | React admin over an existing API via data providers | The API is not resource-shaped, or screens are workflow-shaped rather than record-shaped | Client-side by default; the server must enforce independently |
| [AdminJS](https://adminjs.co/) | Autogenerated Node admin over existing ORM models | Anything beyond CRUD on those models | Role-based, coarse; per-row scope needs custom work |
| [Filament](https://filamentphp.com/docs) | Laravel resources, forms, tables, actions | Multi-tenant scope conditions and approval chains | Integrates with Laravel policies, which is the right seam — use them |
| [Directus](https://directus.com/docs) | An admin and API over an existing schema | The domain needs commands rather than table edits | Granular field and row permissions; genuinely capable, schema-centric |
| [Payload](https://payloadcms.com/docs) | Content-shaped domains where the admin is part of the product | Operational queues, reconciliation, money movement | Access-control functions per collection; good, but content-oriented |
| Retool, Appsmith, Budibase, ToolJet | Internal tools fast, with database and API connectors | Version control, testing, review, and audit expectations of a real product; per-row scope is usually bolted on | Varies; frequently the weakest part. Verify before trusting it with privileged operations |

A note on the low-code tools: they are legitimate and often correct for a small internal
back office. They are a poor fit when the console is customer-visible, when its behavior must
be tested in CI, or when an auditor will ask who changed what. Judge them on the audit and
authorization model, not the demo.

## The decision table

Read down the column that matches the project. Ties go to the hybrid.

| Factor | Adopt a framework | Hand-build |
|---|---|---|
| Managed entities | Many, similar shape | Few, each with distinct workflow |
| Lifecycle complexity | Mostly create/edit/archive | Real state machines with preconditions and side effects |
| Authorization | Role-only | Scope, attribute, or relationship conditions |
| Regulated data | None | Present |
| Tenancy | Single-tenant | Multi-tenant with cross-tenant operations |
| Money movement | None or read-only | Refunds, payouts, ledger adjustments |
| Who maintains it | A small team wanting defaults | A team that will own it long-term |
| Is it a product surface | Internal only | Customers or partners see it |
| Volume | Low, human-paced | High, queue-driven |

One row is close to decisive on its own: if privileged operations move money, change access,
or touch regulated data, the authorization and audit layer must be yours regardless of what
renders the screens.

## The hybrid pattern

This is what most teams should do:

1. Adopt the framework for scaffolding, generic CRUD, lists, and forms over the
   record-shaped tail of the domain.
2. Hand-build the high-risk command surfaces: transitions, approvals, refunds, access
   changes, bulk operations, and anything with a reason-capture or dual-control obligation.
3. Keep authorization and audit in your own domain services either way, so both halves of the
   console enforce the same policy and write the same audit events.

The failure mode this avoids is a console with two authorization models — the framework's for
the screens it generated, and yours for the screens you wrote — which is how a hidden action
in one half becomes a callable endpoint in the other.

Record the boundary explicitly. Every capability in the manifest should be attributable to
one side of it.

## What adoption never waives

Adopting a framework changes who writes the code. It does not change the contract.

- Every capability still needs a real server operation, a server-side policy, an
  authoritative data source, and evidence.
- Privileged mutations still need audit events with actor, target, reason, and result.
- High-risk commands still need safeguards, idempotency, and a recovery path.
- Roles still need negative tests proving forbidden actions are rejected by the server, not
  hidden in the interface.
- The framework's own admin routes are part of the attack surface and belong in the
  authorization test matrix.

A framework may satisfy a requirement. Verify that it does rather than assuming, then record
the evidence path like any other. "The framework handles it" is a claim, and
[verification.md](verification.md) treats unverified claims the same regardless of who made
them.

## Recording the decision

Write the outcome to `decisions[]` with `status: confirmed`, naming what was adopted, what
was hand-built, and where the boundary sits:

```text
{ "id": "dec.admin-framework",
  "decision": "Filament for record CRUD; hand-built payout and refund surfaces",
  "reason": "Scoped approval and dual control exceed Filament's resource permissions",
  "evidence": ["docs/adr/0004-admin-framework.md"],
  "status": "confirmed",
  "appliesTo": ["payout.approve", "order.refund"] }
```

Also set `platform.stack.adminFramework`. A later agent auditing this console needs to know
which half of it it is looking at.
